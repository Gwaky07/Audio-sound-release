# audio-sound 工作流

## 默认成品标准

本仓库默认对齐“自然、清晰、稳定的中文口播最终成品标准”，不是最大强度降噪。

只要用户在这个仓库里让你“处理音频”或“用 skill 处理”，默认就按最终版执行。
默认成品本身就是保守的人声保护链，而不是临时预览。

核心目标：

- 首先保证字头、辅音、句尾和音色完整
- 不因追求绝对安静而牺牲可懂度
- 整体响度稳定，但保留自然句间动态
- 已确认的呼吸、口水音、停顿残留再做局部处理
- 最终音频只放到 `output/修音成品/`
- 输出文件命名为 `修音版_<原音频文件名>.wav|mp3`
- 同名已存在时自动递增为 `_01`、`_02`，方便排查不同版本
- 中间 wav/mp3 默认清理，避免用户误把过程文件当成最终版

默认目标为约 `-19 LUFS`、`-3 dBTP`；不同来源可覆盖目标，但不得用响度目标掩盖局部音量塌陷。

## 默认模式选择

### 1. `auto`

这是默认少人工成品模式。

适用场景：

- 日常口播、课程、旁白和配音交付
- 希望 Codex 自动选安全候选，减少人工干预
- 质量守门通过后自动交付，异常才人工复核

特点：

- 先产出 `natural` 安全基线
- 修音意图下强制竞争 `final_repair_best`（完整 `final` 链），再按诊断和 `doctor` 能力尝试：`clarity_leveling_safe`、`noise_cleanup_safe`、`respiro_breath_safe`、`deepfilter_denoise_safe` 和局部 duck 精修
- Respiro 只允许高置信检测后的有限局部 duck；DeepFilterNet 必须关闭 post-filter；门限和数字硬静音禁止自动启用
- 两个单模型候选分别通过后才可生成 `model_combined_review`，组合候选始终要求可绑定双 ASR
- 报告会记录 `capability_plan`、`repair_scorecard`、`delivery_incomplete_for_repair_intent`、`model_applied`、`model_succeeded`、`fallback_used`、收益、伤害、候选评分、淘汰原因和最终回退理由
- 若只能回退 `natural_baseline`，必须标记修音意图未完成，不得当作最终修音交付

### 2. `natural`

这是保守自然基线模式，也可作为 `auto` 回退结果。

适用场景：

- 用户强调自然度、吐字清晰和音量稳定
- 未确认具体噪声类型，需要先保护原声
- 不想跑候选搜索，只要 mastering

特点：

- 默认不启用自动呼吸衰减、模型降噪、自适应降噪、门限或硬静音
- 只做 55 Hz 高通、1.25:1 轻压缩和整体响度统一
- 具体问题通过复核后再局部补修

### 3. `reference-style`

这是旧版呼吸清理风格，只在用户明确要求时使用。

适用场景：

- 用户强调自然度
- 不希望清得太狠
- 主要是低响度、自然口播交付

### 4. `reference-legacy`

仅用于复现旧版交付或缺陷对照。它包含极限停顿清理、硬静音和桥接清理，不得作为新成品默认模式。

### 5. `final`

这是例外模式，不是默认模式。只有用户明确要求平衡交付时才用。

该模式保留不可变 `raw_wav`，把 Respiro、辅助停顿边缘和噪声型频谱证据合并为授权呼吸窗口。首轮按前置停顿底噪处理，母带后重新检测并执行窄窗口补处理；最终高于局部底噪 3 dB 的确认残留会以 `confirmed_breath_residual_after_retry` 阻止交付。频谱和增益 preservation 比较只排除这些有记录的授权窗口，其余语音仍完整守门。

### 6. `voice-isolate`

用于用户能提供同文件噪声窗口的情况，重点是压环境噪声和非人声残留。

### 7. `review`

用于输出清理结果并附带复核信息，方便后续人工点名问题节点。

## 实际执行顺序

### 第一步：环境核查

先运行 `doctor`。

必须看清楚：

- `ffmpeg` 是否可用
- `ffprobe` 是否可用
- `DeepFilterNet` 是否可用
- Respiro-en 是“真的本地可用”，还是只有 fallback 可用

### 第二步：主流程清理

默认基础链路固定为：

1. 保留原始语音波形、采样率、声道数和立体声布局
2. 55 Hz 高通，仅去除不可用超低频
3. 1.25:1 慢启动轻压缩，控制异常峰值
4. 整体响度统一并导出 WAV/MP3

Respiro-en 和 DeepFilterNet 不属于固定默认链，但可由 `auto` 在缺陷证据、运行能力和严格守门同时满足时生成固定安全候选。自适应强降噪、门限和自动静音仍不允许自动启用。

用户只说“修音”但没有给具体要求时，先跑 `auto`：建立 `natural` 基线，再按诊断尝试白名单候选；`quality_guard.release_blocked=true` 的候选不得交付，增强失败时回退自然版。

自适应判断只允许四个白名单结果：

- `baseline`：没有高置信缺陷，保持自然基线。
- `leveling_gentle`：动态范围偏宽，只做受限轻压缩。
- `noise_review`：稳定底噪和候选噪声窗口存在，只进入人工复核，不自动开启强降噪。
- `manual_review`：检测到削波等高风险问题，停止自动加强。

Codex/GPT 是控制层而不是任意 DSP 生成器。它可以读取诊断、选择白名单档位、说明理由和要求局部复核，但不能直接构造任意滤镜参数或绕过 `allow_destructive_cleanup=false`。多声道只在诊断阶段临时下混为单声道分析，实际处理和最终 WAV/MP3 必须保留源声道与采样率。

DeepFilterNet 后允许做“防吞字恢复”，但必须遵守连续语音上下文：

- 只恢复夹在真实语音前后之间的短缺口
- 不恢复开头静音区、长停顿区、段落间隙里的孤立声音
- 如果报告里的 `deepfilternet_dropout_repair_windows` 出现在 0 秒附近或长静音区，要重点怀疑是误恢复杂音
- 出现用户说“多出来一个音频”时，先比对 raw、DeepFilterNet、mastered、delivered 四个阶段的局部能量和频谱

默认最终交付使用 `auto`。`reference-legacy` 仅用于旧版问题复现。

### 第三步：频谱图复核

主流程完成后，不直接宣布完成。

必须做：

- 整体频谱图
- 必要时做局部频谱图
- 在聊天窗口展示图

### 第四步：节点巡检

如果用户说还有问题，或给出具体时间点：

1. 先抓该节点前后 0.5 到 1.5 秒的局部频谱
2. 再看该节点是否是：
   - 呼吸音
   - 气口
   - 口水音
   - 停顿残留
3. 同时分阶段比对 raw、DeepFilterNet、mastered、delivered，确认问题是原始残留、降噪误伤、后处理误切，还是恢复规则误恢复
4. 确认后再做精确时间窗处理

对“黑色断档/吞字”的判断：

- 不要只看黑块，要量化该点前后 60 到 120ms 的峰值和 RMS
- 如果短黑块前后仍有连续语音能量，且报告里该窗口被 `continuous_speech_context` 保护，通常不是吞字
- 如果语音核心窗口被压到接近 `-120 dB`，才按吞字或误切处理
- 停顿清理可以把真正停顿压黑，但不能把字尾或起字一起切掉

### 第五步：节点精修

节点精修优先用 `exact_window_cleanup.py`。

原则：

- 只修确认过的窄窗口
- 能硬静音就硬静音
- 会伤到起字时改成更窄窗口或更轻 duck
- 修完要重新导出 MP3

### 第六步：终验

终验必须同时检查：

- 最终 WAV 路径
- 最终 MP3 路径
  - 必须来自 `output/修音成品/`
- 节点前后频谱图
- 最终响度与峰值
- 文件命名是否符合 `修音版_原名`，重名时是否递增 `_01/_02`
- `audio_process_report.json` 里 Respiro-en 是否真实成功
- `deepfilternet_dropout_repair_windows` 是否没有落在开头孤立杂音或长停顿区

## 什么时候可以算完成

满足下面几点才算完成：

- 用户点名的问题节点已修掉
- 新问题没有被引入
- 没有明显吞字
- `breath_cleanup.status=PASS` 且 `final_residual_windows` 为空
- 频谱图证据能对上
- 响度没有被带偏
- 最终交付文件在 `output/修音成品/`
- 最终交付文件名正确，且不同运行不会同名覆盖或混淆
