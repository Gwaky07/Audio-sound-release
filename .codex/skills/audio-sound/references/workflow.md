# audio-sound 工作流

## 默认成品标准

本仓库当前默认要对齐的是“严格中文口播最终成品标准”，不是普通预处理。

只要用户在这个仓库里让你“处理音频”或“用 skill 处理”，默认就按最终版执行。
除非用户明确提出别的目的，否则不要把需求理解成：

- 先出一个轻处理版本
- 先随便试一版
- 先做一个保守预览
- 先听听看再说

核心目标：

- 呼吸音、气口、口水音、停顿细丝尽量清干净
- 不要误吞后面起字
- 频谱图里明显的停顿残留要尽量压黑
- 响度保持在当前线程已认可范围附近
- 最终音频只放到 `output/修音成品/`
- 输出文件命名为 `修音版_<原音频文件名>.wav|mp3`
- 同名已存在时自动递增为 `_01`、`_02`，方便排查不同版本
- 中间 wav/mp3 默认清理，避免用户误把过程文件当成最终版

当前线程中已经通过验收的参考电平大致是：

- `-24.8 LUFS`
- `-3.0 dBTP`
- `mean -25.9 dB`
- `max -3.0 dB`
- `LRA 5.4`

## 默认模式选择

### 1. `reference-legacy`

这是默认严格成品模式，也是目前最接近用户认可结果的模式。

适用场景：

- 用户要求“处理干净”
- 用户要求“紫色细丝也尽量没有”
- 用户要求“按本线程认可成品标准来”
- 用户后续还会继续点具体时间节点让你精修

特点：

- 主流程后还会继续做更强的停顿/桥接/残留清理
- 更适合口播、讲解、课程这种要明显去呼吸痕迹的音频

### 2. `reference-style`

这是例外模式，不是默认模式。只有用户明确要求更自然、更克制时才用。

适用场景：

- 用户强调自然度
- 不希望清得太狠
- 主要是低响度、自然口播交付

### 3. `final`

这是例外模式，不是默认模式。只有用户明确要求平衡交付时才用。

### 4. `voice-isolate`

用于用户能提供同文件噪声窗口的情况，重点是压环境噪声和非人声残留。

### 5. `review`

用于输出清理结果并附带复核信息，方便后续人工点名问题节点。

## 实际执行顺序

### 第一步：环境核查

先运行 `doctor`。

必须看清楚：

- `ffmpeg` 是否可用
- `ffprobe` 是否可用
- `DeepFilterNet` 是否可用
- Respiro-en 是“真的本地可用”，还是只有 fallback 可用

### 第二步：主流程清理

基础链路固定为：

1. Respiro-en 检测呼吸段
2. SpectraMini 风格呼吸控制和口水音/小爆点处理
3. DeepFilterNet 降噪
4. 仓库后处理和响度整理

DeepFilterNet 后允许做“防吞字恢复”，但必须遵守连续语音上下文：

- 只恢复夹在真实语音前后之间的短缺口
- 不恢复开头静音区、长停顿区、段落间隙里的孤立声音
- 如果报告里的 `deepfilternet_dropout_repair_windows` 出现在 0 秒附近或长静音区，要重点怀疑是误恢复杂音
- 出现用户说“多出来一个音频”时，先比对 raw、DeepFilterNet、mastered、delivered 四个阶段的局部能量和频谱

默认最终交付优先使用：

- `reference-legacy`，如果目标是严格成品

### 第三步：频谱图复核

主流程完成后，不直接宣布完成。

必须做：

- 整体频谱图
- 必要时做局部频谱图
- 在聊天窗口展示图

### 第四步：节点巡检

如果用户说还有问题，或给出具体时间点：

1. 先抓该节点前后 0.5 到 1.5 秒的局部频谱
2. 再看该节点是否是：
   - 呼吸音
   - 气口
   - 口水音
   - 停顿残留
3. 同时分阶段比对 raw、DeepFilterNet、mastered、delivered，确认问题是原始残留、降噪误伤、后处理误切，还是恢复规则误恢复
4. 确认后再做精确时间窗处理

对“黑色断档/吞字”的判断：

- 不要只看黑块，要量化该点前后 60 到 120ms 的峰值和 RMS
- 如果短黑块前后仍有连续语音能量，且报告里该窗口被 `continuous_speech_context` 保护，通常不是吞字
- 如果语音核心窗口被压到接近 `-120 dB`，才按吞字或误切处理
- 停顿清理可以把真正停顿压黑，但不能把字尾或起字一起切掉

### 第五步：节点精修

节点精修优先用 `exact_window_cleanup.py`。

原则：

- 只修确认过的窄窗口
- 能硬静音就硬静音
- 会伤到起字时改成更窄窗口或更轻 duck
- 修完要重新导出 MP3

### 第六步：终验

终验必须同时检查：

- 最终 WAV 路径
- 最终 MP3 路径
  - 必须来自 `output/修音成品/`
- 节点前后频谱图
- 最终响度与峰值
- 文件命名是否符合 `修音版_原名`，重名时是否递增 `_01/_02`
- `audio_process_report.json` 里 Respiro-en 是否真实成功
- `deepfilternet_dropout_repair_windows` 是否没有落在开头孤立杂音或长停顿区

## 什么时候可以算完成

满足下面几点才算完成：

- 用户点名的问题节点已修掉
- 新问题没有被引入
- 没有明显吞字
- 频谱图证据能对上
- 响度没有被带偏
- 最终交付文件在 `output/修音成品/`
- 最终交付文件名正确，且不同运行不会同名覆盖或混淆
